# Grubhub

> Grubhub is a US online food-ordering and delivery marketplace. Its partner platform lets
> point-of-sale vendors, online-ordering providers, delivery aggregators and enterprise restaurant
> brands ingest menus, receive and manage Marketplace orders, control merchant availability and
> schedules, run last-mile delivery on Grubhub's courier network (Grubhub Connect), onboard
> merchants, and export merchant reports.

Generated 2026-09-17 by the API Evangelist enrichment pipeline. Grubhub serves no /llms.txt of its
own (https://developer.grubhub.com/llms.txt returns 404), so this file is generated from Grubhub's
own twelve OpenAPI documents plus artifacts derived from them. Nothing here is invented.

## What is real, and what is not

- Twelve first-party OpenAPI documents, 91 operations and 3 egress webhooks, fetched verbatim from
  https://developer.grubhub.com/resource/partner-docs/api-docs/ on 2026-09-17.
- Production base URL: https://api-third-party-gtm.grubhub.com
- Preproduction base URL: https://api-third-party-gtm-pp.grubhub.com
- Authentication: X-GH-PARTNER-KEY header (UUID), issued through Grubhub partner onboarding.
  There is no self-serve API signup and no public API key.
- A real OAuth 2.0 authorization server (RFC 8414 metadata, dynamic client registration, PKCE,
  scopes openid + diner) exists for diner-facing ordering integrations.
- Grubhub publishes NO MCP server, NO A2A agent card, NO client SDK on any package registry, NO CLI,
  NO status page, NO changelog and NO security.txt. Do not claim otherwise.

## Things an agent must know before calling this API

- Two merchant identifier spaces coexist. `merchant_id` is the legacy identifier; `merchant_long_id`
  is the long form. Only the path-parameter name tells them apart, and both are typed as bare
  strings. Sending the wrong one produces a 404, not a validation error.
- There is no idempotency mechanism anywhere. 56 mutating operations, zero replay protection.
  Retrying a POST is not safe; read state back before retrying.
- Several merchant-wide writes are asynchronous: they return a batch_id or job_id and must be polled
  at a matching /{batch_id}/status or /jobs/{job_id} operation.
- Errors are not RFC 9457. Grubhub Connect returns {code, message}; Reporting returns {message};
  most Marketplace 4xx responses declare no body at all.
- Exactly one operation declares a 429, and no operation declares any rate-limit response header.
- Reversal operations exist (cancel a delivery, request a refund, delete a schedule override,
  deactivate a merchant, close/open now) but NO time window is published for any of them.
- New Marketplace orders arrive by webhook. Grubhub configures webhook URLs by hand; a partner
  cannot set or change them through the API.
